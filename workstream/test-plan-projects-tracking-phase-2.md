## A Note on This Wave's Testable Surface

Every deliverable is prompt text in three trees plus parity blocks in one test file. There is no application code. As in wave 1, every row below is one of two kinds:

- **Static (Layer 1, executable).** Assertions over markdown in `test/unit/projects-tracking-parity.test.ts`, plus the existing tests that already pin planner, implement, plan and verifier text (LT rows). These prove the text says what the AC requires, in all three trees.
- **Dogfood (Layer 4, observed, D-39).** Behavioural criteria are verified by a **read** of GitHub or git after a named event of **this wave's own `/planner` run**, the first run with a wave issue (#290). The read commands are given exactly. **No row mocks `gh`**, and no behavioural criterion is reported as verified by a static test alone.

One property of this run changes what the dogfood evidence means (A-25): the planner is loaded once, at run start, from main 700bc07, so the wave 2 rules are not in its loaded prompt; each rule lands in the integration branch only when its story merges. Every DF row therefore records its evidence as **`hand-applied (rule merged at S-0xx)`** or **`prompt-driven`**. The first fully prompt-driven run is wave 3's; Phase 6 can be prompt-driven on this run if the close-out is started in a fresh session after the consolidated PR reaches main.

Test-ID series continue wave 1: `PT` parity/static assertions (PT-31 on), `CT` contract shapes (CT-13 on), `LT` existing gates (LT-9 on), `DF` dogfood observations (DF-6 on), `E2E` scenarios (E2E-8 on), `EC` edge cases (EC-41 on), `RT` enumerated tactics (RT-4 on), `RV` document review checks, `A` Design Mode findings (A-19 on).

Planner copies: `.claude/commands/planner.md` (command), `.github/agents/planner.agent.md`, `.kiro/agents/planner.md`. Their merge gates 5, 6 and 13 already differ (D-60), so **every planner assertion is marker-scoped and pins only sentences wave 2 adds**; no planner assertion compares whole files or the pre-existing gate lines.
