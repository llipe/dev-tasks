**Mode:** Design Mode (pre-implementation). No implementation exists yet. Where this plan states a _predicted_ result, that prediction was produced by read-only inspection of the current tree and is marked as such.

### Layer taxonomy used

Per `TESTING.md`:

- **Layer 1** — deterministic foundations. Unit and structural assertions. No socket, no database, no wall clock.
- **Layer 2** — CLI, filesystem, subprocess, distribution, fixtures.
- **Layer 4** — human evaluation. Used only where nothing deterministic is possible; every Layer 4 case in this plan carries a written justification.

`TESTING.md`'s **Contract** layer is `dt verify`-bound and is itself deleted by S-005 AC-5. Section 5 of this plan therefore redefines "contract" for this phase as the four boundaries that survive: the **published-package contract**, the **CLI exit-code contract** (ADR-002), the **three-tree parity contract**, and the **documentation-reference contract**. Those cases are classified Layer 1 or Layer 2, not "Contract".

### Validation methods

| Method                       | Meaning                                                                                                                                                                          |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **automated command**        | A command or in-suite test whose exit status is the verdict. Preferred.                                                                                                          |
| **deterministic inspection** | A scripted, repeatable read (`grep`, `git diff --name-only`, JSON key read) with a fixed expected output. Machine-checkable, not yet wired into the suite.                       |
| **manual check**             | A human judgment. Used only where the property is prose quality, a network-dependent release action, or a decision that has no defined machine form. Each occurrence states why. |

## 2. How This Plan Is Weighted

A deletion cannot be verified by testing the deleted thing. Generic coverage would spend its effort on the 19,600 lines that are leaving and none on the seam. This plan puts its weight on three failure classes and treats everything else as bookkeeping.

| Risk class                    | What it looks like                                                                                                                                                    | Groups  | Cases |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- | ----- |
| **1. Silent dependence**      | Something retained quietly relied on something deleted. The claim under test is that `core/distribution` and `bin/dev-tasks.ts` import nothing from the deleted tree. | A, B    | 22    |
| **2. Silently weakened gate** | A check stops checking rather than fails. The clearest case is `.github/workflows/publish-npm.yml`, which only runs at publish time.                                  | C, D    | 18    |
| **3. Regression**             | A `dt` reference creeps back through a prompt file. The absence test (AC-27) is the guard, so the guard itself is the thing under test.                               | E, F    | 22    |
| Supporting                    | Documentation reference integrity, the pass signal, rollback                                                                                                          | G, H, I | 29    |
| Randomized                    | Property and fuzz tactics over the guard and the gate list                                                                                                            | J       | 4     |

Three findings from read-only investigation reshaped the weighting, and each has a dedicated case:

1. The publish workflow asserts **two** deleted paths, not one. Line 69 asserts `dist/bin/dt.js`; **line 71 asserts `dist/adapters/`**, which S-001 also deletes. S-003 AC-5 names only the first. Release breaks either way (TC-C01, TC-C02).
2. **Five retained-looking parity tests assert the presence of content this phase removes.** Two must be deleted, three must be edited — which contradicts S-002's rule that no retained test is modified except `binaries.test.ts` (TC-F03, TC-F04).
3. The pass signal of **exactly 4 failures is wrong; the measured retained figure is 5** (TC-H03). The enumerations in S-002 AC-5 and the task-list baseline table both name five cases while asserting four.

### 4.2 The four failures — named, and the fifth

Task 0.2 says "record the failing-test list". The specification, S-002 AC-5, and the task-list baseline table all commit to the number **4** in advance. Measured on this branch (`a24e9cb`, which is `main` plus three docs-only commits), the retained, environment-dependent failures are **five**:

| #   | Full test name                                                                                                                                  | File                                          | Cause                | Retained? |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | -------------------- | --------- |
| 1   | `dev-tasks bootstrap commands (integration) > doctor > runs all checks and outputs results`                                                     | `test/integration/bootstrap-commands.test.ts` | environment          | yes       |
| 2   | `dev-tasks bootstrap commands (integration) > doctor > supports --json output with structured check results`                                    | `test/integration/bootstrap-commands.test.ts` | environment          | yes       |
| 3   | `core/distribution/doctor > checkCacheDir > fails when path is not writable`                                                                    | `test/unit/distribution-doctor.test.ts`       | runs as root         | yes       |
| 4   | `core/distribution/update — runUpdate() > edge case: --force with unwritable backup dir > throws error when backup directory cannot be created` | `test/unit/distribution-update.test.ts`       | runs as root         | yes       |
| 5   | `deploy.sh — blocked conditions and edge cases (AC-3, 8.9) > exits 2 when yq is missing from PATH`                                              | `test/unit/infra-script-contract.test.ts`     | `yq` present on PATH | yes       |

Evidence: `pnpm exec vitest run test/unit/distribution-doctor.test.ts test/unit/distribution-update.test.ts test/integration/bootstrap-commands.test.ts` → `Tests 4 failed | 57 passed`; `pnpm exec vitest run test/unit/infra-script-contract.test.ts` → `Tests 1 failed | 41 passed`, with `yq` resolving to `/usr/bin/yq`.

S-002 AC-5 itself enumerates five ("two `doctor` integration cases, one `doctor` unit case, one `update` backup case, one `deploy.sh` case") while asserting four. The task-list baseline table does the same. **The number is an off-by-one in the written signal, not a defect in the plan of work** — but as written it converts a correct run into a failed gate. See §10, finding NV-01.

### 4.3 The signal, sharpened

Counting is the wrong assertion. A count of 5 is preserved if this change breaks one test and coincidentally fixes one pre-existing environment failure — for example, if the branch runs as a non-root user, failures 3 and 4 disappear and two new real regressions would keep the total at five. TC-H02 asserts **set equality over full test names**, with the count as a derived, secondary check. That is the form D-36 should have taken.

## 8. Randomized Tactics and Seed Policy

### 8.1 Seed policy

- Every randomized case takes its seed from `process.env.DT_TEST_SEED`, defaulting to a **fixed literal** so ordinary runs are deterministic. Randomization is opt-in, never ambient in `pnpm run test`.
- On failure the test prints `seed=<value>` and the minimized input as the first line of the assertion message.
- Replay: `DT_TEST_SEED=<value> pnpm exec vitest run <file> -t "<case name>"`.
- Retry budget: a non-reproducing failure is retried at most **3 times**, then classified `inconclusive` with the environment triple from §4.1 recorded.

### 8.2 Tactics

| ID     | Tactic                                                                                                                                                                                                                                                                                                                                           | Layer | Method            |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----- | ----------------- |
| TC-J01 | **Property test over the guard matcher.** Generate strings from a grammar: `{dt, adt, dt-, DT, dev-tasks dt, width, CloudTrail} × {" ", "-", "`", "/", EOL} × {init, extract, catalog, scope, verify, ctx, foo}`. Property: the matcher fires if and only if the token is a standalone `dt` followed by a known subcommand, or a known path form | 1     | automated command |
| TC-J02 | **Injection fuzz.** For a seeded random sample of 40 tracked files under the scanned roots, insert one randomly chosen `dt` reference at a random line, run the guard, assert failure naming that file, revert. Detects scan-scope holes that a hand-written positive control misses                                                             | 1     | automated command |
