# Compliance Test Plan — claude-runtime-parity

**Status:** Design complete — test-first implementation required
**Scope:** Parent tasks 1.0–11.0; GitHub issues #169–#179; milestone `v0.13 — Claude runtime parity and enforcement delivery`
**Sources:** `workstream/tasks-claude-runtime-parity-plan.md` (no PRD/spec exists for this scope — the task list and its published issues are the requirement source); issue bodies for #169–#179 (Acceptance Criteria sections, fetched via `gh issue view <n> --json body -q .body`)
**Companion:** `workstream/traceability-matrix-claude-runtime-parity.md`

## Verdict / implementation entry criteria

The scope is testable without adding dependencies beyond the repository's existing Vitest/shell tooling. Implementation MUST begin by creating the listed deterministic tests, observing each fail for the intended missing behavior (per repository default: every parent task begins with a failing test), then implementing only enough to make the relevant test pass. All acceptance criteria have positive and negative/edge coverage in the traceability matrix, subject to two explicit decision points that this plan accounts for rather than silently resolving:

- **Task 4.0 (#172) — withdraw-vs-scaffold.** This plan's assertions are written to pass under _either_ resolution's documentation requirement (no file may claim a Claude delivery mechanism that does not exist). The code-scaffolding branch (detection + write path in `install.ts`) is conditional and only enters scope if 4.1 is decided as "scaffold."
- **Task 7.0 (#175) — gate-ownership honesty.** This plan assumes option (a) (the issue's recommendation) as the target resolution and designs CP-07 and its traceability rows around it. If implementation instead lands option (b) (documented expected failure), the CP-07 pass criteria for the honesty sub-assertions do not apply and the single expected failure must be linked to a tracking issue instead — this is called out explicitly in CP-07 and is not to be silently treated as a pass.

No production GitHub mutation is authorized by this plan. All `gh` interaction in deterministic tests goes through the stub CLI described below; no test may reach the network, mutate this repository's real branches/PRs/tags, or use production credentials.

## Test environment and fixtures

- **Repository fixture:** a fresh clone/worktree with no uncommitted files, plus a scratch temp directory per `install --profile <x>` invocation under test (never the working repository itself) so install/update assertions cannot corrupt this repo's own `.claude/`, `.kiro/`, or root files.
- **`gh` CLI stubs (mirrors the infra-engineer precedent's `test/fixtures/infra/bin/{aws,flyctl,supabase,yq}` pattern):** a dedicated `test/fixtures/claude/bin/gh` stub is prepended to `PATH` for git-guard and planner-merge-gate tests. It MUST:
  - log full argv to a `GH_STUB_LOG` file for assertion,
  - be independently controllable for `gh pr view --json baseRefName -q .baseRefName` (returns a configurable base branch — `main`, an `integration/*` name, or a nonexistent PR number to simulate lookup failure),
  - be independently controllable for `gh pr view --json state,mergedAt` (returns `MERGED`/`OPEN`/`CLOSED` plus a mergedAt timestamp or `null`),
  - be independently controllable for `gh repo view --json defaultBranchRef` (returns a configurable default branch name, including non-`main` values such as `master`/`trunk`, and a simulated failure mode),
  - simulate "`gh` unavailable" and "`gh` unauthenticated" by a wrapper test harness that removes the stub from `PATH` or makes it exit non-zero, rather than by modifying the stub's default behavior, so the fail-closed path (task 9.0 decision) is exercised without touching a real network,
  - never contact GitHub, never mutate any real issue/PR/branch/tag, and reuse the existing `test/fixtures/infra/bin/gh` stub's argv-logging convention rather than inventing a second incompatible one, unless the two stub sets need to diverge in controllable response shape (they do, for the reasons above), in which case both MUST remain independently discoverable and documented.
- **`git` fixture repos:** ephemeral bare + working-copy repo pairs created per test with a controllable default branch (`main`, `master`, `trunk`) and controllable current branch, so `git-guard.sh`, `branch-guard.sh`, and the default-branch resolution fallback chain can be exercised without touching the real repository's branches.
- **Claude PreToolUse payload fixtures:** synthetic JSON stdin payloads (`tool_name`, `tool_input.command`, or `tool_input` shapes for MCP tool calls) covering every rule under test; malformed/empty payloads MUST also be represented per the hook's documented fail-open contract (except where task 9.0 introduces an explicit fail-closed exception, which MUST be tested as the exception, not the default).
- **Agent/command corpus fixtures:** a copy (or in-place read) of every `.claude/agents/*.md` and `.claude/commands/*.md` for frontmatter/body parsing (`model:`, `tools:`, invocation-instruction scanning, size cap).
- **Model identifier validity:** the "allowed set" of `model:` values MUST be sourced from the same authority the implementation task cites (task 6.0's own verification step: "confirm the model identifiers used are current and valid before committing"); tests assert _membership in the declared allowed set_, not liveness against a live model registry, to keep the suite deterministic and offline.
- **Environment evidence:** record OS, Node/pnpm versions, command, commit SHA, test seed (where applicable), and sanitized output for every manual scenario.
