## What changed and why (plain language)

Wave 1 changes the written rules the agents follow, not application code. After this wave, publishing a feature's stories to GitHub also creates two container issues — one for the whole PRD and one for the wave — and nests each story under its wave, so GitHub itself shows the hierarchy and a progress bar. Stage labels such as "ready" and "in progress" are retired from the label rules because a linked pull request already shows that state. Every story issue now carries exactly one status comment that the developer edits in place as work progresses, so anyone can see where a story stands from the issue alone. Setting up a GitHub Project is a documented, one-time human step with a runbook; no agent ever writes to the Project, GitHub's own automations move items. One test file pins all of this identically across the three platform trees (Claude, Copilot, Kiro), and a guard test fails if any prompt or doc ever gains a Project write command.

Everything the six stories promised is on the integration branch, and the four corrections routed between stories (S-006 sub-tasks 6.1b to 6.1j) are applied. The one new finding of this rollup comes from live GitHub, not from the text: GitHub only treats a pull request as "linked" to an issue when that pull request targets the default branch. The six story PRs targeted the integration branch, so none of them linked its issue, and the six story items on Project 5 still read `Backlog`. The conventions are correct as written; the PRD's expectation that a story PR moves the Project to "In progress" needs a sentence for the planner case in wave 2.
