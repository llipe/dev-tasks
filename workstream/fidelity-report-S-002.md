## What changed and why (plain language)

When a product plan's stories are first put on GitHub, the publishing procedure now does more than create one issue per story. It first looks for a "parent" issue for the whole plan and a parent issue for the current wave of work, reusing them if exactly one of each already exists, creating them if none does, and stopping to ask if it finds more than one so it never guesses. Every story issue is then linked underneath its wave, and the wave underneath the plan, using GitHub's built-in sub-issue feature; the procedure reads the links back and writes down whether all of them took. The upshot is that GitHub's own project views can show per-wave progress with nothing extra for anyone to maintain.

Two smaller things changed alongside. The question that used to ask whether the user wanted a parent issue is gone, because the parent structure is now always built. And the procedure now says the `gh` command line is the normal way to talk to GitHub, with the alternative access method optional, matching what the rest of the repository already says.

The wave parent issue has a fixed layout: its scope, a placeholder for the branch name that will be filled in later, links to the specification and story list, and the list of stories, with no checkboxes to tick, because progress is read from the linked stories and the issue's status comment instead.

Everything the story asked for is present, the three platform copies carry the same text, and an automated test pins each rule in all three. The four drift items below are small: two places where the delivered text goes slightly beyond or sits slightly ahead of the written spec, one layout the spec never defined (the plan-level parent issue's body), and one pre-existing line this story did not touch.
