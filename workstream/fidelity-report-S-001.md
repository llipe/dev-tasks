## What changed and why (plain language)

The rulebook that every agent follows when it touches GitHub (the "github-ops" guide, kept in three identical copies for three AI platforms) now describes how a whole product plan and each of its delivery waves get their own tracking issue, on top of the per-story issues that already existed. Three new labels (`level: prd`, `level: wave`, `level: story`) say which of the three an issue is, in matching shades of indigo so they read as one family. The two labels that tried to say "ready" and "in progress" by hand are retired, because GitHub already shows that from the linked pull request; a "deferred" label is added for work parked on purpose. Issues that are just containers (a plan or a wave) no longer need a work-type or a priority label.

The guide also now holds the one template for a "status comment": a single comment per issue, written to be read from a phone, that an agent updates in place as work progresses instead of posting a trail of new comments. It is found by an invisible marker on its first line, so nothing needs to remember a comment id.

Finally, the two copies of the guide that had told agents to prefer a different GitHub access method (MCP) over the `gh` command line were brought into line with the third copy and with the project rules: `gh` is the primary path; MCP is optional. A new automated test pins every one of these conventions in all three copies so they cannot drift apart silently.

Everything the story asked for is present, identical across the three copies, and covered by the test. The four drift items below are small: one wording question about why the two labels were retired, two intentional additions that go slightly beyond the letter of the story, and one roadmap row that will be refreshed when the wave ships.
