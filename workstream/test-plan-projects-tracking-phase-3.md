## A Note on This Wave's Testable Surface

This is the first projects-tracking wave with application code. `TESTING.md` § Known limitations says regex parity pins prove presence, not meaning. So this plan splits the evidence on purpose:

- **Behaviour (Layer 1, `MU`).** Pure stages (`classify`, `map`, `roadmap`, `plan`, `planfile`) and the two `gh` callers (`snapshot`, `apply`) are tested in process. `snapshot` and `apply` get an injected `GhRunner`. For `apply`, the runner is a **fake GitHub model**: an in-memory repository that applies each write to its own state. Assertions are about the **resulting repository state**: which labels sit on which open issue, which parent each issue has, how many marker comments exist. They are not internal call counts (TESTING Layer 1 "must not"). Call shapes are asserted only where the contract is the call itself: `--body-file`, no `gh project`, no `gh label delete`, and read-only `--plan`.
- **CLI (Layer 2, `MC`).** `tsx bin/dev-tasks.ts migrate projects …` runs as a child process against a **fake `gh` executable**. The fake is a Node script that replays fixture JSON per argv and appends each argv to a log file. It sits in a purpose-built PATH directory that holds only it and a `node` symlink to `process.execPath` (TESTING PATH-fragility note: Homebrew directories hold both `node` and a real `gh`). This exercises the real `execFile("gh")` runner, exit codes, stdout and stderr, without replacing the system under test at its own entry point (TESTING Layer 2 "must not"; A-85).
- **Prompt text (Layer 1 static, `PT`).** S-019, S-016 and S-017's mode text are pinned in `test/unit/projects-tracking-wave-3-parity.test.ts`, byte-identical across `.claude`, `.github` and `.kiro`. They prove presence only. Meaning is checked in Audit Mode and by the dogfood rows.
- **Dogfood (Layer 4, `DF`).** S-017 AC-3 migrates this repository live, with the owner's approval. The evidence is the committed plan file plus `gh` reads given verbatim below. No DF row mocks `gh`.

## Contract Validation Scenarios (`activity-contract-test-design`)

The plan file is a contract among four parties. `--plan` produces it. The human reads and answers it. github-ops writes answers and approval into it. `--apply` consumes it and writes states back. The `GhRunner` is the contract between the module and `gh`. Exit codes and `--json` are the contract with github-ops.

| ----- | ------------------------------ | --------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------ |
| CT-24 | Plan header                    | provider-driven | `--plan` → human, github-ops, `--apply`   | Line 1 `# Migration plan: <owner>/<repo>`.
