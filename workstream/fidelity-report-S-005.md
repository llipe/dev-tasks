## 1. Human-readable summary

When dev-tasks is first set up in a repository, the setup guide (the `activity-init` skill) walks the user through a few one-time chores, such as protecting the main branch. This story adds one more recommendation to that guide: create a GitHub Project board so the planning issues the toolkit publishes (a PRD, its waves, their stories) appear on a board that GitHub itself keeps up to date. The guide gains a short four-sentence paragraph saying so and pointing at a new step-by-step procedure, `docs/runbooks/runbook-configure-github-project.md`.

The procedure deliberately changes as little as possible. It keeps GitHub's own Status columns (Todo, In Progress, Done) and the built-in rules that move cards between them, tells GitHub to add only issues (not pull requests) to the board, removes five columns the template adds that nothing in dev-tasks uses, and describes three views to build by hand because GitHub offers no way to script them. No agent ever moves a card: a pull request linking an issue and the issue closing when work ships are what move it. Skipping the board changes nothing else.

The paragraph is identical in the three platform copies of the guide (Claude, Copilot, Kiro), the runbook follows the repository's runbook template and passes the documentation-structure check, the index of runbooks lists it, and tests were written and seen failing before any guide or runbook text was written. The one thing not yet done, by design, is running the procedure for real on this repository, which needs the owner's go-ahead because it creates a Project. Until that run happens, one assumption stays unproven: that GitHub turns on the card-moving rules the runbook relies on without anyone touching them. The live run should record, for every rule on the fresh board, its name and whether it is on.
