## A Note on This Wave's Testable Surface

Every deliverable is prompt text in three trees, one runbook, one `TESTING.md` table and one test file. There is no application code, no API and no database. So this plan has exactly two kinds of verification, and each row below says which one it is:

- **Static (Layer 1, executable).** Assertions over markdown in `test/unit/projects-tracking-parity.test.ts`, plus the existing gates that the new files must satisfy (`tsx core/checks/run.ts` under `lint`, `test/unit/runbook-set.test.ts`, `test/unit/skill-parity-init.test.ts`, `test/unit/developer-command-collapse.test.ts`, `test/unit/memo-write-reliability.test.ts`). These prove the **text says** what the AC requires, in all three trees.
- **Dogfood (Layer 4, observed, D-39).** Behavioural criteria — publish creating a live hierarchy, an agent creating and editing a status comment, the runbook producing a Project — are verified by **reading GitHub after a real event** with the `gh` read commands given in the `DF-*` rows. Each `DF-*` row names the event that produces the evidence and the issue it will be recorded against in `TESTING.md`'s Dogfood checks table. **No row in this plan mocks `gh`**, and no behavioural criterion is reported as verified by a static test.

Test-ID series: `PT` parity/static assertions (new file), `CT` contract-shape assertions (static, on the templates and field vocabularies), `LT` existing lint/test gates the delivery must pass, `DF` dogfood observations, `E2E` black-box scenarios (each step marked static or dogfood), `EC` edge cases, `RT` randomized/enumerated tactics, `A` Design Mode findings.
