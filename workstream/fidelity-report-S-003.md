## What changed and why (plain language)

Until now, a developer agent working through a story was only encouraged to leave the occasional note on the GitHub issue. Someone checking progress from a phone had to open the pull request or a file in the repository to learn which step was in progress, which branch and pull request were involved, whether the checks had passed, and whether anything was stuck.

After this change the rule is firm: every story issue carries exactly one status note, created when the first step finishes and rewritten in place at every later step, when the pull request opens, each time a quality check is recorded, and whenever work is blocked. The note is always the same one; it is recognised by an invisible tag on its first line, so nothing has to remember a number for it, and no second note is ever posted. If two tagged notes are ever found, the older one is used and the duplicate is reported so a person can remove it. If a write fails, the failure is reported but never stops the work.

A second rule covers the case where a developer works alone, without the multi-story planner. After the pull request opens and again when it is ready for review, the developer looks up whether the story belongs to a larger wave of work. If it does, the developer updates the story's line in the wave's own status note (creating that note if the wave has none yet). If it does not — which is the case for every story in this wave, because they were published before the wave structure existed — the developer simply reports that there was no parent to update. Under the planner, the planner owns the wave note and the developer leaves it alone.

The layout of the note is not repeated here; it is kept in one place (the GitHub conventions document) and referred to by name, so the three platform copies of this procedure stay in step. All three copies carry word-for-word the same text, an automated test pins every rule in all three, and the rule was applied to this very story's issue as its first real use: issue #272 has exactly one tagged note, edited in place rather than re-posted.

The four drift items below are small: a fourth report value the specification did not list, a bootstrapping detail in the first real use (the note could not exist before the rule did), a gap in the shared template that this story inherits rather than creates, and an under-specified detail of the wave-note creation path that only the next wave will exercise.
