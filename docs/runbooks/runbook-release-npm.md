# Cut an npm release

A release is a human action. The script computes the version, writes the
changelog, commits, tags, and pushes; the tag push is what triggers
publication. Agents do not create, move, or delete tags — the tag is the
trigger, and triggering a publish is a human decision.

Note which script this documents. `templates/scripts/release.sh` is the
consumer-facing template delivered into your repository. dev-tasks' own
`scripts/release.sh` is a different, larger file that releases dev-tasks
itself. The steps below describe the template; the dev-tasks maintainer flow
is the same shape with the same guards.

## Preconditions

- On the default branch, with a clean working tree. The script refuses both
  otherwise and exits `2`.
- The commits since the last tag follow Conventional Commits — the changelog
  is generated by grouping them, so an unconventional subject lands in the
  wrong section or none.
- `CI` unset, or `INFRA_HUMAN_APPROVED=1`. The script refuses to run
  unattended; that guard is the point, not an obstacle.
- npm publishing is configured: the `npm` environment exists on the
  repository and trusted publishing (OIDC) is set up for the package.

## Steps

1. Confirm what will be released:

   ```bash
   git log "$(git describe --tags --abbrev=0)"..HEAD --oneline
   ```

2. Dry-run it. This writes nothing:

   ```bash
   ./scripts/release.sh minor --dry-run
   ```

   Read the proposed version and changelog entry before continuing.

3. Run it for real with the increment you chose:

   ```bash
   ./scripts/release.sh minor
   ```

   It generates the `CHANGELOG.md` entry, sets `package.json`'s version,
   commits, creates an annotated tag, and pushes both.

4. The tag push starts two workflows:
   - `.github/workflows/publish-npm.yml` — runs `validate`, builds, verifies
     `dist/`, packs, and publishes with provenance. It resolves the version
     from the tag and overwrites `package.json` if they disagree, so the tag
     is the source of truth, not the committed version.
   - `.github/workflows/release-bundle.yml` — builds the distributable bundle
     and attaches it to the GitHub Release.

## Verification

```bash
gh run list --workflow publish-npm.yml --limit 1
npm view @llipe.com/dev-tasks version
gh release view "v<version>"
```

Both workflows are green, npm reports the new version, and the release
carries its bundle asset. A green tag push with no npm version change means
the publish job failed after the build — read its log rather than re-tagging.

## Rollback

A published npm version cannot be replaced. Do not delete and re-push a tag
to "fix" a release: the tag is already consumed by both workflows, and npm
will reject a re-publish of the same version.

Roll forward instead — cut the next patch release with the fix. For a release
that must not be used at all, `npm deprecate @llipe.com/dev-tasks@<version>
"<reason>"` leaves it installable but warns every consumer, which is the
honest state of the world. Within the 72-hour window `npm unpublish` exists,
but it breaks anyone who already installed; prefer deprecation.

## Escalation

A failed publish job with a green build is usually an npm auth or provenance
problem: check that the `npm` environment and trusted publishing are still
configured for the package, and escalate to whoever owns the npm
organization. A tag that triggered nothing means the tag name did not match
`v[0-9]+.[0-9]+.[0-9]+` — inspect it before creating another.
